# Askly: сохранность данных и проверки

## Контракт сохранения

API возвращает `Survey.revision`. Сохранение конфигурации требует
`expected_revision`; обновление JSON и увеличение revision атомарны.
Несовпадение возвращает 409 `SURVEY_REVISION_CONFLICT`, без перезаписи.
Некорректные вопросы, диапазоны, варианты и canvas-ссылки отклоняются до записи.
Пустой список вопросов разрешён для первоначального черновика.

Отправка ответа требует `survey_revision`. Сервер под блокировкой проверяет
активность опроса и ревизию, валидирует ответ, сохраняет схему и расходует
приглашение в одной транзакции. Устаревшая форма получает конфликт, приглашение
остаётся доступным. Версия нужна и при отправке без персонального токена.

Редакторы вопросов, canvas и дизайна сохраняют снимок отправленной правки.
Изменения, внесённые во время запроса, остаются dirty. Локальные черновики
хранятся в sessionStorage по опросу/редактору. Черновик от старой ревизии не
перебазируется автоматически: пользователь может скачать JSON либо явно
отбросить его и получить текущую схему. Недоступное/повреждённое хранилище
показывает предупреждение. Это восстановление в пределах вкладки, не облачное
хранение черновиков и не гарантия восстановления после очистки браузера.

## История

Новые ответы содержат `survey_revision`, `config_snapshot` и
`snapshot_source='submission'`. Снимок содержит реально показанные вопросы,
контакты и legacy-подписи; декоративные настройки не дублируются в каждой записи.
DB-trigger запрещает менять этот снимок, но разрешает статус и заметку.

Карточки, аналитика и CSV используют снимок. Разные версии группируются отдельно.
Для старых записей миграция может сохранить только доступную сегодня схему:
такие записи помечаются `legacy_backfill`, а не выдаются за точную историю.
Если схема отсутствует, ответы остаются видимыми по ключам и фактическим типам.
Удалённые до миграции названия восстановить автоматически невозможно.

## Обновление существующей установки

1. Подготовить резервную копию и проверить обновление на копии БД.
2. Для Node применить новые `server/migrations` штатным runner; для Supabase
   использовать отдельную hosted-цепочку по `server/MIGRATION.md`.
   Миграция `007_survey_revisions.sql` добавляет ревизии и историю.
3. Развернуть API и frontend согласованно: прежние клиенты без ревизии больше
   не могут сохранять конфигурацию или отправлять ответы. Проверить открытые
   до обновления формы и предложить пользователям обновить страницу.
4. Не переписывать ранее применённые SQL-файлы и не сбрасывать рабочий volume.

В ходе разработки миграции проверялись только на изолированном PostgreSQL.
Рабочая БД пользователя этим изменением не обновлялась.

## Проверки

- `npm run check`: единая локальная проверка frontend/backend/архитектуры.
- GitHub workflow: проверка push/PR и PostgreSQL integration job.
- Vercel build запускает frontend `check`, включая lint/typecheck/test.
- Интеграция на настоящем PostgreSQL: fresh bootstrap, конкурентные миграции,
  rollback DDL, погашение одного токена конкурентными запросами, конфликты
  ревизий, неизменяемость истории, владельцы/grants, hosted SQL privileges.
- Hosted fixture моделирует минимальные managed-схемы: это не проверка реального
  OAuth-провайдера, Supabase gateway, Storage или Edge lifecycle.

В браузере на API с отдельной PostgreSQL БД проверены правка во время delayed
save, восстановление после смены разделов, конфликт с другим редактором,
явная загрузка актуальной версии, черновики дизайна/canvas, отправка ответа
и сохранение старого названия в карточке/аналитике после переименования.

Структурное разделение сохраняет CSS-классы и каскад: стили перенесены целыми
последовательными секциями, исходный текст проверен на точное восстановление.
Поведение проверяется повторно после извлечения компонентов.
