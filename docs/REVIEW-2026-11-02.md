Проверен снимок `5d8f5be4b4d8618b314f1656dc5f1ccf1428964c` в ветке
`codex/opros-vercel-deploy`. Это зафиксированные после CLI-деплоя исходники,
а не SHA, из которого Vercel автоматически собирал приложение через Git.
Preview: https://opros-7m3j897lb-relect-666.vercel.app.

Параллельные изменения `WelcomeScreen`, `DottedSurface`, новых fixtures и UI
в исходной рабочей папке исключены. Продуктовый код при ревью не исправлялся.
Внешние проверки использовали только чтение. Изолированные проверки API
работали с подставной БД; браузерные проверки — с перехваченными GET-запросами.
Реальные ответы, опросы и приглашения для воспроизведения багов не изменялись.

## Оценка по четырём направлениям

| Направление | Вывод |
| --- | --- |
| Качество кода | Frontend существенно перегружен состоянием и ответственностями. Backend компактнее, но бизнес-правила и SQL находятся в HTTP handlers. Успешная сборка не означает прохождение quality gates. |
| Структура монорепозитория | `survey`, `server`, `supabase` выделены, однако нет корневого npm workspace, общих contracts, единой цепочки миграций и общего проверочного pipeline. |
| Архитектура | Переиспользование API между Node и Edge работает. Основные пробелы — серверная модель опроса, версия опубликованной анкеты, конкурентные изменения, история ответов и согласование режимов развёртывания. |
| Баги | Подтверждены несовместимость старых приглашений, неотправляемый опрос без контактов, потеря правок, неполный CSV, гонка фильтров и падение пустой формы. Есть дополнительные проверяемые дефекты контрактов и эксплуатации. |

P1 ниже означает исправление до расширения эксплуатации и новой рассылки.
P2 — отдельную необходимую задачу после P1. Замечания не являются исправлениями.

## P1: функциональные дефекты и потеря данных

### R1. Три существующих приглашения несовместимы с новым API

Место: [server/src/routes/tokens.ts:12](../server/src/routes/tokens.ts#L12),
[старый генератор](../survey/src/lib/supabase.ts#L496).

`TOKEN_PARAMS` допускает только 32 шестнадцатеричных символа. Старый клиент
генерировал 16 символов base36. В текущем Supabase все три существующих токена
имеют длину 16; GET разрешения одного из них вернул HTTP 400 до обращения к БД.
Та же схема используется для отметки открытия, удаления и перегенерации.
Сама отправка ответа проверяет токен по БД, поэтому здесь не утверждается,
что любой ответ по такой ссылке обязательно теряется. Подтверждён отказ
перечисленных операций и статистики открытия.

Исправление: поддержать оба исторических формата для lookup либо выполнить
миграцию совместимости с сохранением ранее разосланных ссылок. Новые токены
продолжать генерировать криптографически. Нужен тест legacy-токена из БД.

### R2. Опрос с отключёнными контактами нельзя отправить

Место: [серверная схема](../server/src/routes/responses.ts#L40),
[клиентская проверка](../survey/src/lib/contactsBlock.ts#L167),
[отправка формы](../survey/src/pages/SurveyPage.tsx#L208).

Конструктор позволяет отключить контакты, имя и телефон. Клиент в таком
состоянии считает контактный шаг заполненным и передаёт пустые строки.
API всегда требует непустое имя и телефон длиной минимум пять символов.
В живых данных `survey_id=9` уже имеет `contacts_block.disabled=true` и
отключённые имя/телефон. Изолированное воспроизведение: `uiAccepts=true`,
`apiStatus=400` для такого payload.

Исправление: сервер должен загружать конфиг опроса и проверять поля по его
настройкам. Простое удаление обязательности всех контактов не заменяет это правило.

### R3. Устаревший конфиг молча затирает новое сохранение

Место: [PUT config](../server/src/routes/surveys.ts#L168),
[редактор вопросов](../survey/src/components/admin/QuestionsTab.tsx#L143),
[редактор дизайна](../survey/src/components/admin/DesignTab.tsx#L124).

PUT заменяет весь JSON без версии/ETag/compare-and-swap. Два редактора читают
одну версию; первый меняет вопрос, второй — оформление. Оба сохранения дают
200, но второй возвращает старый текст вопроса. Это воспроизведено через
настоящие Fastify routes с подставной БД: статусы `[200,200]`, итоговый title
снова `Original`. Предварительный GET в DesignTab не устраняет гонку между GET и PUT.

Исправление: версия конфига и условный UPDATE с 409 на конфликт; затем UI
сравнения/повторного применения правок. Нужны тесты параллельных редакторов.

### R4. CSV не содержит динамические ответы

Место: [exportToCSV](../survey/src/components/admin/ResponsesTab.tsx#L52).

Экспортирует фиксированные CRM-колонки и вообще не обращается к `r.answers`.
На момент чтения 11 из 56 реальных ответов содержат динамические поля. Эти
поля не попадают в CSV даже при их отображении в карточке заявки. Это потеря
информации в выгрузке, а не удаление строк в базе.

Исправление: строить колонки по схеме/версии опроса, включать текстовые,
множественные и scale-ответы, обрабатывать удалённые вопросы и `__other`.
Добавить тест результата CSV для динамического опроса.

### R5. Редактирование анкеты меняет представление исторических ответов

Место: [рендер ответов](../survey/src/components/admin/ResponsesTab.tsx#L287),
[запись ответа](../server/src/routes/responses.ts#L82).

Карточка перебирает текущие `survey.config.questions`, а ответ хранит только
`survey_id` и значения по question ID. Удаление вопроса скрывает его старые
ответы в UI; переименование показывает прежние значения под новой формулировкой.
Версия анкеты или snapshot текста вопросов вместе с ответом не сохраняются.
Вывод подтверждён схемой записи и рендера; реальные анкеты не редактировались.

Исправление: версия опубликованной анкеты и связь ответа с этой версией.
До миграции UI обязан показывать orphan answers, а не терять их при обходе
только текущего списка вопросов.

### R6. Обязательные вопросы и согласия контролируются только браузером

Место: [API schema и запись](../server/src/routes/responses.ts#L40),
[проверки UI](../survey/src/pages/SurveyPage.tsx#L208).

API принимает произвольный object `answers`, не проверяет его по вопросам
анкеты, не получает `consentChecks` и не сохраняет подтверждение обязательных
согласий. Изолированный POST с неизвестным вопросом и вложенным object вместо
ответа получил 201. Проверка активности опроса и приглашения есть, но этого
недостаточно для проверки самого результата прохождения.

Исправление: единая серверная проверка answer ID/type/options/range и
обязательности полей; версия правил согласий и запись их подтверждения.
Нужны отрицательные API-тесты, не зависящие от клиентской валидации.

## P1: воспроизводимость развёртывания

### R7. Чистый Supabase нельзя восстановить одной цепочкой миграций репозитория

Место: [hosted security migration](../supabase/migrations/005_hosted_api_security.sql#L8),
[создание profiles](../server/migrations/003_auth_profiles.sql),
[создание lead_projects](../server/migrations/006_lead_projects.sql).

Supabase 001–004 не создают `profiles`, `survey_access`, `lead_projects` и
`_migrations`, но Supabase 005 сразу выполняет ALTER/REVOKE для этих таблиц.
Они есть в текущей базе благодаря другой истории обновлений. На новой базе
эта последовательность не завершится. Первичное создание хеша пароля также
выполнено отдельно от checked-in миграции и требует документированного bootstrap.

Это проверка зависимостей SQL, а не заявленный успешный fresh-install тест.
Исправление: одна каноническая цепочка application schema с явным Supabase
overlay, воспроизводимый bootstrap и smoke-test пустой базы в CI.

### R8. Docker Compose не соответствует текущему серверу

Место: [Postgres init](../docker-compose.yml#L20),
[environment API](../docker-compose.yml#L38),
[JWT bootstrap](../server/src/app.ts#L72).

Compose монтирует Supabase SQL в обычный `postgres:16-alpine`; SQL использует
роли `anon`/`service_role` и Supabase storage schema, которых такой образ не
создаёт. Кроме того, Compose передаёт `ADMIN_API_KEY`, но не `JWT_SECRET` и
`ADMIN_PASSWORD`. Production bootstrap теперь требует signing secret не
короче 32 символов; API key больше не служит этим секретом.
nginx проксирует только `/api`, без `/uploads` и WebSocket upgrade.

Конфликт подтверждён конфигурацией; фактический Docker-start в этом ревью
не выполнен. Исправление: согласовать self-hosted deployment как отдельный
поддерживаемый профиль и проверять его запуском с пустым volume.

## P2: другие подтверждённые баги

### R9. Ответ старого запроса перезаписывает новый фильтр заявок

Место: [ResponsesTab.load](../survey/src/components/admin/ResponsesTab.tsx#L110).

У загрузки нет AbortController, generation ID или защиты от устаревшего ответа.
В Edge на изолированном снимке перехвачены только GET-запросы: ответ для
«Новые» задержан, ответ для «Закрыто» отдан первым, затем отпущен старый ответ.
Итог: `selectedFilter="Закрыто"`, `staleRowVisible=true` для строки RACE-NEW.
Моки после проверки сняты, в БД ничего не записывалось.

Исправление: отмена запросов либо проверка поколения/ключа запроса перед
изменением data, total, loading и error. Тот же шаблон загрузки проверить
в остальных списках.

### R10. Пустая анкета без контактов падает после «Начать»

Место: [isAnswered и canGoNext](../survey/src/components/survey/DynamicSurveyForm.tsx#L127).

При `questions=[]` и `contacts_block.disabled=true` число шагов равно нулю,
но `canGoNext` вызывает `isAnswered(questions[0])`. В Edge с GET-fixture
получено `Cannot read properties of undefined (reading 'type')`.
Такая комбинация достижима через настройки конструктора и не отвергается API.

Исправление: состояние пустого опроса и запрет публикации непроходимого конфига.
Серверная проверка должна валидировать nested config, а не только `type: object`.
Изолированный PUT с `config={}` сейчас тоже получает 200.

### R11. Live autosave не сообщает об ошибке и не создаёт барьер сохранения

Место: [flushSave](../survey/src/pages/SurveyPage.tsx#L160).

Таймер через 400 мс запускает `void updateSurveyConfig(...)` без catch,
подтверждённой версии, очереди или UI состояния ошибки. `persistCanvasConfig`
возвращается до завершения HTTP-запроса; изменения отображаются локально и
сбрасывают форму прохождения. Закрытие страницы до таймера или ошибка PUT
оставляют несохранённые правки без сообщения. Наличие таймера само по себе
не обеспечивает autosave. Вывод по коду; действующие опросы не редактировались.

Исправление: общий autosave controller с latest-value queue, состояниями
dirty/saving/error, flush и обработкой конфликтов из R3.

### R12. Проверка домена iframe допускает посторонний домен

Место: [isHostAllowedForIframeEmbed](../survey/src/lib/questionMedia.ts#L87).

Проверяется `host.endsWith('youtube.com')` без границы DNS-имени; преобразователь
также использует `includes`. `https://evil-youtube.com/embed/abcdef` проходит
эту проверку, хотя это не YouTube и не его поддомен. Аналогичная ошибка есть
для других suffix-проверок. Это обход заявленного allowlist, не доказательство
доступа iframe к DOM родителя или выполнения кода в его origin.

Исправление: точное совпадение или `host.endsWith('.' + allowedHost)`, HTTPS,
минимальные iframe permissions и тесты deceptive hostname.

## Качество и структура: что мешает сопровождению

1. `AdminPage.tsx` — 1084 строки: auth bootstrap, роли, выбор платформы,
   навигация, тема, sidebar, URL parsing, overlays и набор внутренних компонентов.
   `QuestionsTab.tsx` — 1007 строк; `SurveysListTab.tsx` — 1097.
   Это несколько независимых ответственностей, а не только превышение размера.
2. Два глобальных CSS-файла содержат 11443 непустых строки. Общие controls,
   состояния и overlay rules не имеют одного component owner. MUI, собственный
   CSS, Tailwind и Framer Motion сосуществуют без общего контрактного слоя.
   Настраиваемые цвета конкретного опроса сами по себе не являются дефектом.
3. Типы домена, Supabase client и старый Data API CRUD смешаны в
   `survey/src/lib/supabase.ts`. Backend вручную дублирует их в `models.ts`;
   серверный ContactsBlockConfig не содержит клиентского `disabled`, canvas
   types также расходятся. JSON Schema не выводится из этих моделей.
4. `lib/contactsBlock.ts` импортирует validator из `components/survey/.../utils`;
   `LeadsTab` импортирует status constants из `ResponsesTab`. Направление
   зависимостей не отражает domain/shared/component boundaries.
5. По обходу статических runtime imports от `main.tsx` не используются
   `SurveyForm`, `lamp`, `lib/logger`, `surveyConfig`, `ws-client`.
   Это кандидаты на удаление после проверки внешних consumers, не разрешение
   удалить их только по результату графа.
6. `main.tsx` eagerly импортирует все страницы, а публичная форма — editor/DnD
   код. Чистая сборка создаёт один JS chunk 1.96 MB / 558 KB gzip. Пользователь
   публичного опроса загружает и административную часть. Нужны route/editor
   boundaries для lazy loading; перенос всех файлов без этого проблему не решит.
7. Backend разделён на routes/lib/db/ws/services, что лучше одного index-файла.
   Но routes одновременно владеют JSON Schema, ACL, SQL, транзакциями и
   notifications. Для изменения правила прохождения нужно менять transport.
   Авторизацию, application use cases и persistence стоит выделять по доменам.
8. Root содержит orphan `package-lock.json`, но не содержит workspace
   `package.json`. Нет общего contracts package и CI, который проверяет web,
   API, миграции и Edge-артефакт вместе. Сборка Vercel не запускает lint/test.

Целевая раскладка, без обязательной смены технологий:

```text
apps/web/src/
  app/                 providers, routes, shells
  pages/               composition страниц
  features/            surveys, editor, responses, invitations, leads, auth
  ui/                  общие controls, overlays и состояния
apps/api/src/
  bootstrap/           Node bootstrap и composition
  modules/             use cases по тем же доменам
  infrastructure/      db, storage, notifications
packages/contracts/    runtime schemas и выведенные TypeScript types
packages/database/     канонические application migrations
supabase/functions/    тонкий hosted adapter и инфраструктурные overlays
```

Начинать следует с контрактов и тестов, затем разделить крупные компоненты,
после этого выполнять механические переносы. Отдельный backend rewrite,
микросервисы или новая UI-библиотека для исправления перечисленных багов не нужны.

## Порядок исправления

1. R1/R2: сохранить работоспособность старых ссылок и существующего опроса без контактов.
2. R3/R5/R6: версия анкеты, серверная проверка и сохранность исторических ответов.
3. R4/R9/R10/R11: CSV, гонки запросов, пустые состояния и надёжное сохранение.
4. R7/R8: воспроизводимый bootstrap и честно поддерживаемые deployment profiles.
5. Общие contracts, границы компонентов, lint/CI, lazy loading, dependency updates и R12.

Успешный preview не является production acceptance. Наличие конкретного
рабочего бэкенда также не устраняет баги фронтенда и историю дрейфа схемы.
