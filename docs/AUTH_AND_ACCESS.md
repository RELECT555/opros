# Авторизация и доступ к опросам

Документ фиксирует **целевую модель** (пользовательские кабинеты, OAuth, изоляция опросов) и **текущее состояние** кода. Нужен, чтобы при переносе на другой бэкенд или другой IdP не потерять требования и схему прав.

**Связанные файлы в репозитории:**

| Что | Где |
|-----|-----|
| Клиент Supabase (данные + будущий Auth) | `survey/src/lib/supabase.ts` |
| Сессия админки (отдельно от OAuth-пользователей) | `survey/src/lib/adminSession.ts`, `survey/src/lib/api-client.ts` |
| Логин админки по паролю / JWT | `server/src/routes/auth.ts` (и см. `requireAdminKey` в middleware) |
| Схема Postgres сейчас | `server/DATABASE.md`, миграции `server/migrations/` |

---

## Продуктовые правила

1. Пользователь после входа видит **упрощённый кабинет**: свои опросники, без чужих.
2. Пользователь **создаёт** опросники; владелец записи — его учётная запись.
3. **Чужие** опросники не видны, пока **глобальный администратор** не выдаст явный доступ (по опросу или списку).
4. Вход желательно с **личной Google** и **рабочей Microsoft** (Entra ID / Microsoft 365).

## Текущее состояние в коде (реализовано)

- Миграция **`server/migrations/003_auth_profiles.sql`**: таблицы `profiles`, `survey_access`, колонка `surveys.owner_id`.
- API **`server`**: Bearer — либо JWT пароля (`POST /api/auth/login`), либо `access_token` Supabase; секрет проверки — `SUPABASE_JWT_SECRET` в `.env`. Список `GLOBAL_ADMIN_EMAILS` выставляет флаг глобального админа в `profiles` при каждой синхронизации.
- Эндпоинт **`POST /api/admin/surveys/:id/share`** `{ "email": "..." }` — только пароль-админ или OAuth с `is_global_admin`; пользователь с таким email должен уже существовать в `profiles` (хотя бы один вход через OAuth).
- Фронт **`survey`**: экран входа — Google, Microsoft (Azure), пароль администратора; данные админки идут через **`api-client`** → **`VITE_API_URL`** (в `.env` фронта). На сервере для локальной разработки задайте **`FRONTEND_URL=http://localhost:5173`** (или ваш порт Vite), иначе CORS заблокирует вход по паролю.
- Ошибка Supabase `Unsupported provider: provider is not enabled` — в Dashboard → **Authentication → Providers** включите **Google** и/или **Azure**, задайте Client ID/Secret; в **URL Configuration** добавьте redirect: `http://localhost:5173/admin` (и прод-URL при необходимости).
- Публичная выдача опроса по slug и отправка ответов **без** Bearer не изменены.

Ранее (до реализации): в `surveys` не было владельца; часть админки ходила напрямую в Supabase — для режима «свой бэкенд» используйте `api-client` и общую Postgres с сервером.

## Целевая архитектура входа (рекомендация)

**Провайдеры:** не путать с библиотекой MSAL на клиенте.

| Канал | Реализация в связке Supabase | Примечание |
|-------|------------------------------|------------|
| Google (личная и Workspace) | `supabase.auth.signInWithOAuth({ provider: 'google' })` | Настройка в Dashboard Supabase + OAuth-клиент Google |
| Microsoft (рабочая почта) | `supabase.auth.signInWithOAuth({ provider: 'azure', options: { scopes: 'email' } })` | Регистрация приложения в Microsoft Entra ID; в Supabase провайдер **Azure** |

**MSAL** имеет смысл только если нужны специфичные сценарии Microsoft (Graph, сложные политики, нативные клиенты). Для веб-входа «Google + работа Microsoft» обычно достаточно OAuth через Supabase.

При **переезде на свой бэкенд** те же провайдеры подключаются к вашему сервису (Passport, OIDC, или hosted IdP: Auth0, Keycloak, Clerk и т.д.). Важно сохранить:

- стабильный **субъект пользователя** (UUID или `sub` из IdP, маппинг в вашу таблицу `profiles`);
- выдачу **сессии/JWT** с `user_id` и при необходимости ролью `global_admin`.

## Целевая модель данных (Postgres)

Ниже — логическая схема для миграции. Имена таблиц/колонок можно адаптировать, смысл сохранить.

### Профиль пользователя

- Таблица `profiles` (или расширение к `auth.users` в Supabase):
  - `id` UUID PK, совпадает с `auth.users.id` **или** с вашим `users.id` на своём бэкенде.
  - `email`, `display_name`, опционально `avatar_url`.
  - `is_global_admin` boolean (или отдельная таблица `global_admins` с UUID — удобнее для аудита).

### Владение опросом

- В `surveys` добавить: `owner_id UUID NOT NULL` (FK → `profiles.id`), индекс по `owner_id`.
- Существующие строки перед включением NOT NULL: назначить системного владельца или nullable + бэкфилл.

### Выдача доступа к чужому опросу

- Таблица `survey_access`:

  - `survey_id` FK → `surveys(id)`
  - `user_id` FK → `profiles(id)`
  - `granted_by` UUID (кто выдал — обычно глобальный админ)
  - `granted_at` timestamptz
  - UNIQUE (`survey_id`, `user_id`)

### Правило видимости (для списков и API)

Пользователь `U` видит опрос `S`, если выполняется хотя бы одно:

1. `S.owner_id = U.id`
2. существует строка `survey_access (S.id, U.id)`
3. `U.is_global_admin = true` (или `U` в `global_admins`)

Публичная страница прохождения опроса (`/survey/:slug`) может оставаться отдельным контуром по `slug` + `is_active`, без привязки к владельцу респондента.

## Row Level Security (Supabase)

Если данные опросов читаются **напрямую из Postgres через Supabase**, политики RLS должны повторять правило видимости выше:

- `SELECT` на `surveys` для авторизованного: владелец OR EXISTS `survey_access` OR глобальный админ.
- `INSERT` на `surveys`: `owner_id = auth.uid()` (или только админ — по продукту).
- `UPDATE`/`DELETE`: владелец или глобальный админ (уточнить политику удаления).

При **только своём бэкенде** (без прямого anon-доступа к таблицам) RLS можно не включать на публичном API, а проверять те же условия в middleware сервиса — логика та же, что в этом документе.

## Разделение ролей: не смешивать контуры

| Роль | Назначение |
|------|------------|
| **Глобальный админ** | Видит всё, выдаёт `survey_access`, системные настройки. |
| **Автор опросов (пользователь)** | Видит только свои опросы + явно расшаренные. Входит через Google/Microsoft. |
| **Текущий «admin JWT»** | Парольная админка; при внедрении OAuth стоит **свести к одной модели** (например, глобальный админ только через Supabase/IdP + `is_global_admin`) либо явно документировать два контура до миграции. |

## Чеклист при переносе на «нормальный» бэкенд

1. Поднять или сохранить IdP: Google + Microsoft OIDC; маппинг в `profiles`.
2. Миграции Postgres: `owner_id`, `survey_access`, `is_global_admin` / `global_admins`.
3. Все эндпоинты списка/редактирования опросов фильтровать по правилу видимости.
4. Отозвать или ограничить прямой доступ anon-ключа Supabase к таблицам, если раньше был открыт.
5. Обновить этот файл, если сменились названия таблиц или правила.
